# 内容指南

Polaris 把文字视为界面的一部分，而不是设计完成后补上的说明。每一个词都会增加界面噪音，因此目标不是“写得多”，而是让商家知道发生了什么、下一步做什么以及结果是什么。

## 四条基本原则

### 内容与设计共同工作

- 只保留理解和行动必需的信息。
- 熟悉且无歧义的符号可以代替文字；陌生图标仍需要可见标签或 tooltip。
- 组件支持副文案不代表每个场景都需要副文案。
- 不能靠长段帮助文字弥补错误的信息架构或控件选择。

### 保持精简

- 使用最短且不会丢失含义的表达。
- 删除标题、正文、按钮之间的重复。
- 单句界面文案通常不加句号；多句内容保持正常标点。
- 精简不能删除风险、后果、限制、费用或恢复方式。

### 像商家一样说话

- 使用普通词汇和商家实际使用的术语。
- 避免内部系统名、数据库名、团队名和错误代码。
- 英文使用自然缩写形式，例如 `can't`、`don't`；其他语言遵循各自自然表达。
- 历史指南建议英文约七年级阅读水平，核心目标是快速理解，不是机械计算分数。

### 推动下一步行动

- 一个区域突出一个最重要的下一步。
- 指令和动作优先用动词开头。
- 把复杂任务分成可完成的步骤，使用渐进披露。
- 不写 “you can…” 这类许可式填充词，直接说明动作和结果。

## 标题、按钮、链接和列表

### 标题

- 英文使用 sentence case；专有名词保持正式写法。
- 标题说明下方内容，不写成完整介绍段。
- 工作型区域可以直接用名词；首次理解、空状态或引导场景可以使用更自然的动词短语。
- 不用标点、全大写或多余加粗制造层级。

### 按钮与菜单动作

- 动作采用 `{verb} + {noun}`，上下文明确时可只保留动词。
- 常见命令可用 `Save`、`Cancel`、`Close`；破坏性动作必须写出具体对象。
- 标签必须让商家预见点击后的结果，不能用 `Next` 掩盖实际收费、发布或删除。
- 菜单按照使用频率、流程或风险排序，不按内部代码顺序。

### 链接

- 只在需要跳转到补充信息或另一个位置时使用链接。
- 不使用 `click here` 或单独的 `here`。
- 链接文本描述目的地或获得的信息；`Learn more` 需要由上下文或可访问名称补足主题。
- 同一屏幕避免堆放多个 `Learn more`，优先把必要信息直接写进任务流。

### 列表

- 顺序不重要用项目符号，步骤或优先级重要用编号。
- 用完整引导句和冒号引出列表。
- 项目保持相同语法结构和粒度。
- 单句或短语列表不加句号；只要有一项包含多句，整组统一加句号。

## 错误信息

错误必须同时回答“影响是什么”和“怎样恢复”。

| 部分 | 要回答的问题 |
|---|---|
| 标题，可选 | 这个问题对商家任务造成什么影响？ |
| 正文 | 具体哪里错了，需要改变什么？ |
| 动作，可选 | 是否有一步即可执行的修复？ |

规则：

- 使用商家的真实对象、字段、数量、日期或状态，避免泛泛的 `invalid`。
- 把字段错误放在字段附近；页面级错误说明整个任务影响。
- 严重程度决定呈现位置和 tone，不能所有错误都用最强红色 Banner。
- Shopify 或 App 自身导致问题时可以承担责任，但不反复道歉。
- 后端细节只在帮助恢复时展示；日志 ID 可以供支持使用，但不能替代解释。
- 没有立即解决方案时，给出可执行的重试、刷新、稍后再试或支持路径。
- 预防优先于报错：在不可逆、收费、数据丢失或权限变化前说明后果。

示例结构：

```text
无法保存商品
请填写商品名称并添加重量，然后重试
[返回商品]
```

不要写：

```text
Validation failed
There are 2 errors on this page
```

## 替代文本

先判断图片在当前上下文中的功能，再决定描述。

- 有信息或交互作用：用简短、具体、上下文相关的替代文本。
- 纯装饰、信息已由相邻文字完整表达、追踪像素：使用空 alt，让辅助技术忽略。
- 不留缺失的 `alt`，否则文件名可能被朗读。
- 不写 “image of” 或文件名；屏幕阅读器已经会宣布图像类型。
- 图标按钮描述动作，例如“搜索”，不是描述形状“放大镜”。
- 复杂图表提供整体结论、数据表或关联长说明，而不是逐个朗读装饰元素。
- 替代文本随上下文变化；同一张鞋图在装饰、教程和商品列表中的文本不同。
- 页面和局部外语文本声明正确 `lang`，保证发音与翻译工具采用正确规则。

SEO 不能破坏无障碍：只加入与图片和购买判断直接相关的关键词，不堆关键词或品牌名。

## 包容性语言

- 在规划和测试阶段引入不同背景与真实经历，不靠单一作者猜测。
- 谈到人时只描述任务所需特征，并使用群体偏好的表达。
- 避免用疾病、残障、种族或性别作为负面隐喻。
- 不把任务描述为“很简单”“只需一下”，直接列出步骤和预计要求。
- 使用 `allowlist`/`blocklist`、`main`/`primary`、`legacy` 等准确术语，避免带有排斥历史的旧词。
- 不假设性别；英文未知时使用 `they/them`，表单仅在业务确实需要时收集相关信息并允许不回答。
- “disabled” 作为 HTML 技术状态可以使用；面向商家的开关动作优先写 `Turn off`、`Inactive` 或具体业务状态。

包容性术语会随社会和产品语境变化，历史词表不能当永久白名单；当前内容仍需由目标语言和目标群体审校。

## 命名

### 默认使用描述性名称

- 功能名优先说明它做什么或代表什么。
- 多数功能不需要品牌化，不要为了显得重要而大写普通名词。
- 名称应符合商家的信息架构，能够与相邻功能区分。
- 第三方 App 名称不得使用 `Shopify` 或 `for Shopify` 制造官方关联。

### 品牌名只用于独立产品

抽象、唤起式名称适合真正独立、需要品牌识别的产品；嵌入主工作流的功能应使用描述性名称。采用名称前检查商标、翻译、文化含义、相似产品和支持团队沟通成本。

### 缩写

- 不创建只有内部团队懂的新缩写。
- 首次出现先写全称，再给缩写。
- 只有目标商家普遍理解的行业缩写可以直接使用，例如 SEO、SKU、QR、USD。
- “普遍理解”必须按市场和语言判断，不能从英文团队经验推断全球理解。

### 组件与图标名称

- 文档名称用单数、sentence case 和功能描述。
- 代码可按语言约定转换，例如 `Empty state` -> `EmptyState`。
- 子组件文档写空格，React 代码可用点号，例如 `Layout section` -> `Layout.Section`。
- 图标按动作或产品对象命名，不按内部隐喻或随意形状命名。

## 数字、日期、时间、货币和单位

历史 Grammar 页给出美国英语的具体格式，但当前 App 必须优先使用商家 locale 和 `Intl` 等本地化能力。

- 不手写 `MM/DD/YY` 等歧义格式。
- 时间使用商家当前时区；跨时区事件明确时区。
- 货币同时考虑 symbol、ISO code、minor units、分组与小数规则。
- 数值和单位之间的空格、复数、计量系统按 locale 处理。
- 不把历史页面中的 USD、12 小时制或 imperial 示例提升为全球默认。

## 内容验收

每个页面至少核对：

1. 首屏是否能看懂当前状态和下一步。
2. 按钮标签是否准确预告结果。
3. 错误是否说明影响与恢复。
4. 文案是否重复组件、标题或页面导航已经表达的信息。
5. 图片、图标和图表是否有正确的无障碍替代。
6. 日期、货币、数字和名称是否可本地化。
7. 是否包含排斥性假设、内部术语、夸张或无根据承诺。
