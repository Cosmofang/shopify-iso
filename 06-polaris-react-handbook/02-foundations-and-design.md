# 基础与设计语言

本章覆盖 Polaris React 站点的 Foundations 与 Design 内容。这里先建立完整主题地图；每项规则都按“仍有效原则、风险边界、当前应用”解释，而不是复刻历史页面。

## 体验价值

Shopify 的体验目标不是让界面显得“像 Shopify”，而是帮助不同规模、地区和能力的商家更快理解状态、做出判断并完成任务。设计决策应能回答：它是否减少认知负担、是否给出清晰下一步、是否能在重复使用中形成可预测性。

历史 Foundations 把价值拆成七个互相约束的方向：considerate 关照上下文与代价；empowering 让商家掌握选择与结果；crafted 处理细节和边界；efficient 缩短高频工作；trustworthy 保持数据、承诺和反馈一致；familiar 利用已知模型；approach 则要求从真实商家问题而非视觉偏好出发。不能只追求“效率”而牺牲确认、可恢复性或信任。

## 可访问性

最低目标是完整任务流可被不同输入、视觉、听觉与认知能力的商家使用。

- 优先原生 HTML 与官方组件，不为视觉效果发明非标准交互。
- 不在后台更新时擅自移动焦点；只有用户触发跳转、打开 overlay 或提交错误后，才把焦点移到必需位置。
- modal、popover 等 overlay 必须管理进入、约束和返回焦点。
- 键盘、屏幕阅读器、语音控制、低视力和色觉差异都属于测试范围。
- 图片和只用图标表达的动作需要与上下文匹配的可访问名称或替代文本。
- 组件自带的无障碍能力不能替代集成后的任务流测试。

历史站点目标为 WCAG 2.1 A/AA；当前项目应以 Shopify 当前要求和适用的 WCAG 版本为准。

## 信息架构

- 用商家的对象和任务组织信息，而不是用内部团队、数据库表或技术模块组织。
- 层级说明“什么最重要”和“什么属于一起”；导航只承担跨区域移动，不替代页面内结构。
- 相同对象在索引、详情、编辑和设置中的名称与状态必须一致。
- 在添加新页面前确认它是否真的需要独立位置，避免功能增长造成导航膨胀。

归档 IA 指南的四个检查问题仍可直接用于评审：商家是否知道自己在哪里；同一内容是否只有一个权威归属但可以有多个入口；当前页面是否避免一次暴露过多选择；结构是否能容纳未来对象和流程而不持续增加顶层导航。

## 国际化与本地化

- 为文本扩展、不同词序、复数、日期、数字、货币和从右到左语言预留结构空间。
- 不把英文词长、字符数或语序当作布局合同。
- 不拼接可翻译句子；给翻译者完整语境。
- 货币展示必须区分 currency code、symbol、decimal separator、grouping 和 minor units。
- 文化相关图像、颜色、图标和隐喻需要单独审查。

### 本地化货币

货币必须区分 store currency 与非店铺货币，并根据上下文选择 short 或 explicit format。相同符号可能代表不同货币；跨币种比较、收费、结算和报表应显示足够的 currency code。对齐遵循本地数字格式和 minor unit，不能假设两位小数、点号小数或逗号分组。用共享 `$` 等符号的多种货币作为测试样例，能较早发现歧义。

## Pro 设计语言

“Pro”指面向高频商家工作的效率、直觉和精度，不等于视觉炫技。

- **Assign meaning**：颜色、图标和状态必须有稳定语义。
- **Increase density**：数据密集场景提高密度，聚焦编辑场景降低密度；密度服务任务。
- **Craft responsive interactions**：交互反馈要及时、可察觉且不过度打断。
- **Make it predictable**：相似外观必须有相似行为，降低重复学习成本。

## 颜色

完整颜色分析已维护在 [01-foundations/color.md](../01-foundations/color.md)。本手册保留三条总原则：颜色有目的、颜色会影响注意力、颜色必须可访问。不能只靠颜色表达状态，也不能为品牌装饰破坏语义角色。

## 布局与密度

- 空间表达亲密度：越接近的元素越像一组。
- 大小、字重和对比建立层级；分隔线主要服务数据行，不应到处切割页面。
- Admin 是工作软件，不是营销网站；优先可扫描、可比较和重复操作。
- 高密度用于索引、表格和批量判断；低密度用于聚焦输入、解释和关键决策。
- 嵌套 surface、圆角和内边距必须有层级逻辑，不能形成无意义的卡片套卡片。

当前响应式实现见 [01-foundations/layout-responsive.md](../01-foundations/layout-responsive.md)，当前 App Home 页面优先使用官方 Templates 和 Compositions。

## 排版

- 排版先表达信息层级，再表达品牌风格。
- 页面标题、区块标题、正文、辅助信息和数值必须有稳定语义。
- 避免用全大写、过低对比或单纯字号制造层级。
- 数字、货币、代码和表格值需要适合扫描与比较的对齐方式。
- 旧 `Text` variants 和 token 名只用于遗留 React 对照；当前使用 `s-heading`、`s-text` 等实际组件合同。

## 深度

深度通过 surface、边界、阴影和叠层表达层级、可交互性和焦点。它不能用于装饰性“漂浮”。

- 阴影必须对应真实层级或交互状态。
- overlay 与基础页面的关系要清楚，不能让多个层级同时争夺注意力。
- inset 内容应看起来属于父 surface，而不是再出现一张独立营销卡。
- 旧 shadow token 值只用于历史诊断。

## 图标

- 图标用于高频、广泛理解的动作和对象；不熟悉的图标需要文字或 tooltip。
- 相同含义始终使用相同图标，同一图标不要承担不同动作。
- filled/outlined、尺寸、光学对齐和点击区域保持一致。
- 装饰图标不进入无障碍树；唯一动作图标必须提供可访问名称。
- 新开发查当前 Shopify icon 资源，不复制旧图标包清单。

## 动效与交互状态

- 动效用于反馈、空间关系、导航连续性和加载进度，不用于吸引无关注意。
- hover、active、focus、selected、disabled 和 loading 必须有可区分状态。
- `disabled` 不应隐藏商家理解“为什么不能做”的必要信息。
- 动画应短、直接、可中断，并尊重 reduced motion。
- 不能用持续动画、庆祝动画或无关提示干扰商家任务。

## 数据可视化

- 每张图回答一个明确问题；先写问题，再选图形。
- 坐标轴、单位、范围、时间区间和比较基准必须明确。
- 颜色序列需可区分且不单独传意，必要时加标签、形状或纹理。
- 表格通常比图表更适合精确读取；图表与表格不是互斥装饰。
- 空数据、部分数据、异常值、加载和失败状态都需要设计。

历史指南用五项质量审查图表：**accuracy** 不歪曲比例与时间；**intuitiveness** 让常见读法无需教程；**engagement** 只帮助探索真实数据；**focus** 突出当前问题而非所有指标；**granularity** 与决策所需时间和数据粒度一致。必须使用真实极值、长标签、零值、负值与缺失区间测试，不用理想演示数据决定图形。

现有实现约束见 [02-components/charts-dataviz.md](../02-components/charts-dataviz.md)。

## Illustrations 与 Sounds

插图和声音是高风险的辅助表达：只有在它们帮助解释状态、确认结果或建立明确反馈时才使用。新 App 不应复制 Shopify 内部插图风格冒充官方，也不应使用声音或动画吸引商家注意力。BFS 的“不分散注意力”要求优先于历史展示案例。

历史 illustration 原则要求有用、同一视觉家族、体贴上下文并保持焦点；颜色、形状、空间、线条和细节都应服务信息。历史 sound 原则要求只对真正紧急或重要事件使用，避免重复骚扰，保持短而可区分，在多设备与静音环境测试，并提供视觉/触觉等非声音通道。对第三方 App，这些原则通常意味着默认不用声音，少用装饰插图。
